# `game/static/game/` — 브라우저 JavaScript와 CSS

> 상위 문서: [game/static/README.md](../README.md)

이 폴더는 Vue나 React 없이 **Vanilla JavaScript + CSS**로 작성된 프런트엔드입니다.

| 파일 | 역할 |
| --- | --- |
| `app.js` | API 호출, 약 1초 폴링, DOM 렌더링, 버튼 이벤트, 채팅 표시 |
| `style.css` | 전체 레이아웃, 모바일 대응, 참가자/단계/채팅 말풍선 스타일 |

## `app.js`의 역할

브라우저에서 현재 방 상태를 기억하고 서버 API와 통신합니다.

대략 다음 흐름으로 생각하면 됩니다.

```text
사용자 클릭/채팅 입력
  ↓
fetch()로 Django API 호출
  ↓
서버가 검증된 snapshot JSON 반환
  ↓
app.js가 DOM을 다시 그림
```

별도로 약 1초 주기로 `sync` API를 호출하여 다른 플레이어의 투표, 채팅, 단계 변화도 받습니다.

## 채팅의 “내 메시지 오른쪽 정렬”

이번 수정에서 서버 메시지 데이터에 `sender_id`를 포함시키고, 브라우저가 현재 사용자의 ID와 비교하도록 했습니다.

개념적으로는 다음과 같습니다.

```javascript
const isMine = message.sender_id === currentUserId;
```

`isMine`이면 내 메시지용 CSS 클래스를 부여하고 오른쪽에 배치합니다. 다른 참가자의 메시지는 왼쪽에 둡니다.

이 방식이 닉네임 비교보다 좋은 이유는 같은 닉네임 문자열이나 표시 이름 변경 같은 UI 요소와 **사용자 식별을 분리**할 수 있기 때문입니다.

시스템 안내 메시지는 특정 사용자의 발언이 아니므로 좌우 대화 버블과 다르게 전체 안내 형태를 유지합니다.

## `style.css`에서 볼 내용

- 전체 3열/반응형 레이아웃
- 패널과 버튼 상태
- 단계 표시
- 참가자 카드
- `.messages` 채팅 스크롤 영역
- 내/상대 메시지 정렬 클래스
- 모바일 화면 크기에 따른 Media Query

## 왜 서버 응답만 화면에 그리나?

멀티플레이 게임에서 브라우저 내부 상태만 바꾸면 다른 사용자와 불일치가 생길 수 있습니다. 그래서 중요한 게임 상태는 서버가 최종 판정하고, 프런트는 그 결과를 표현하는 역할에 집중합니다.

```text
프런트: "3번에게 투표하고 싶다"
서버:   "현재 살아 있는가? 투표 단계인가? 대상이 유효한가?" 검증
서버:   상태 저장
프런트: 새 snapshot을 받아 표시
```

## 새 UI 기능을 추가할 때

예를 들어 “채팅 메시지 시간 표시”를 추가한다면:

1. 서버 state에 이미 시간이 있는지 확인
2. `snapshot.py`가 시간을 반환하는지 확인
3. `app.js`의 메시지 렌더링에 시간 DOM 추가
4. `style.css`에서 작은 보조 텍스트 스타일 추가

게임 판정 자체를 JavaScript에만 구현하지 않는 것이 핵심입니다.
